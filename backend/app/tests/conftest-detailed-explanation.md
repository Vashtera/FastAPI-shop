# conftest.py — построчный разбор от А до Я

Это самый важный файл в тестировании твоего проекта — он не содержит ни одного
теста, только **подготовку окружения**, которую потом используют все тесты
через механизм фикстур. Разберём каждую строку.

---

## Блок 1 — Переменные окружения ДО импорта приложения

```python
import os

os.environ["DATABASE_URL"] = "sqlite+aiosqlite:///./test_shop.db"
os.environ["REDIS_URL"] = "redis://localhost:6379/0"
os.environ["SECRET_KEY"] = "test-secret-key-for-testing-only"
```

**`import os`** — стандартный модуль Python для работы с операционной системой,
в частности с переменными окружения.

**`os.environ["DATABASE_URL"] = ...`** — `os.environ` это словарь, в котором
хранятся все переменные окружения текущего процесса. Присваивая значение по
ключу `"DATABASE_URL"`, мы **программно устанавливаем** переменную окружения,
как будто написали в терминале `export DATABASE_URL=...` перед запуском.

**Почему именно эти три строки, и почему именно ЗДЕСЬ, в самом начале файла:**

Твоё приложение (`app/core/config.py`, класс `Settings`) при своей инициализации
читает переменные окружения — либо из реального `.env` файла, либо (если она уже
установлена) из `os.environ`. Порядок чтения такой: Pydantic Settings сначала
проверяет `os.environ`, и только если там пусто — заглядывает в `.env`.

Если бы эти три строки стояли **после** импорта `app.main` — было бы поздно:
`Settings()` уже создался бы к тому моменту с реальными продакшн-значениями
из `.env`, и тесты работали бы **с настоящей базой данных**, а не с тестовой.
Именно поэтому это первые строки файла, до всех остальных импортов.

**`sqlite+aiosqlite:///./test_shop.db`** — строка подключения к SQLite базе:
- `sqlite` — какая СУБД
- `+aiosqlite` — какой асинхронный драйвер использовать (обычный SQLite
  синхронный, `aiosqlite` — асинхронная обёртка над ним, совместимая
  с твоим async SQLAlchemy кодом)
- `///./test_shop.db` — относительный путь к файлу базы данных (создастся
  прямо в папке где запускаешь тесты)

## Блок 2 — Остальные импорты

```python
import pytest
from httpx import ASGITransport, AsyncClient
from sqlalchemy.ext.asyncio import AsyncSession, async_sessionmaker, create_async_engine
from sqlalchemy.pool import NullPool

from app.database import Base
from app.main import app
from app.services.dependencies import get_session
```

**`import pytest`** — фреймворк тестирования, даёт декоратор `@pytest.fixture`,
без которого этот файл не имел бы смысла — именно pytest распознаёт эти функции
как фикстуры и умеет их автоматически подставлять в тесты.

**`from httpx import ASGITransport, AsyncClient`**:
- `AsyncClient` — асинхронный HTTP-клиент, которым тесты будут "стучаться"
  в твоё приложение (делать `.get()`, `.post()` и т.д.)
- `ASGITransport` — специальный транспорт, о котором подробнее ниже, в блоке
  про фикстуру `client`

**`from sqlalchemy.ext.asyncio import AsyncSession, async_sessionmaker, create_async_engine`**:
- `AsyncSession` — тип асинхронной сессии SQLAlchemy, используется здесь
  только как type hint (подсказка типа) для читаемости кода
- `async_sessionmaker` — фабрика, которая создаёт объекты сессий по запросу
  (не сама сессия, а "конструктор сессий")
- `create_async_engine` — функция создающая **движок** — объект, который знает
  как физически подключаться к БД (пул соединений, диалект SQL и т.д.)

**`from sqlalchemy.pool import NullPool`** — специальный класс "пула без пула",
разберём подробнее ниже.

**`from app.database import Base`** — это тот самый базовый класс, от которого
наследуются все твои SQLAlchemy модели (`User`, `Category`, `Product`).
`Base.metadata` содержит информацию **обо всех таблицах** которые нужно создать
в БД — используется дальше для автоматического создания схемы.

**`from app.main import app`** — это твой реальный объект `FastAPI()`
из `main.py`, тот самый со всеми подключёнными роутерами (`users_router`,
`categories_router` и т.д.). Тесты будут обращаться именно к этому объекту
напрямую в памяти, а не через реальный HTTP-сервер.

**`from app.services.dependencies import get_session`** — импортируем именно
ту функцию-зависимость, которую твои роутеры используют через `Depends(get_session)`
в продакшн-коде. Она нужна дальше — для **подмены** этой зависимости на тестовую
версию.

## Блок 3 — Фикстура `test_engine`

```python
@pytest.fixture(scope="session")
def test_engine():
    engine = create_async_engine(
        os.environ["DATABASE_URL"],
        poolclass=NullPool,
    )
    return engine
```

**`@pytest.fixture(scope="session")`** — превращает обычную функцию в фикстуру.
Параметр `scope="session"` означает: эта фикстура выполнится **ровно один раз**
за весь запуск `pytest` (за всю "сессию" тестирования), а не заново для каждого
отдельного теста. Без указания `scope`, значение по умолчанию — `"function"`
(выполняется заново для КАЖДОГО теста, что было бы избыточно для создания
движка БД — незачем пересоздавать его сотни раз).

**`create_async_engine(os.environ["DATABASE_URL"], poolclass=NullPool)`**:
- Первый аргумент — строка подключения (та самая которую мы установили в
  Блоке 1)
- `poolclass=NullPool` — говорит SQLAlchemy **не использовать пул соединений**

**Зачем нужен `NullPool` именно в тестах:**

Обычно (в продакшене) SQLAlchemy держит несколько **уже открытых** соединений
про запас (пул), чтобы не тратить время на открытие нового соединения при
каждом запросе — это ускоряет работу.

В тестах с SQLite это может создавать проблемы: если несколько тестов
одновременно (или последовательно, но с переиспользованием старого соединения
из пула) работают с одним и тем же файлом БД, могут возникать блокировки
("database is locked") или несогласованное состояние между тестами.
`NullPool` заставляет открывать **новое** соединение при каждом обращении
к БД, что медленнее, но надёжнее и предсказуемее — а в тестах предсказуемость
важнее скорости.

**Почему функция НЕ помечена `async def`, хотя работает с асинхронным движком:**

Само **создание** объекта `engine` через `create_async_engine()` — синхронная
операция (просто конструирует Python-объект, ещё не подключается к базе
физически). Подключение произойдёт позже, при первом реальном запросе.
Поэтому саму фикстуру не нужно делать асинхронной.

## Блок 4 — Фикстура `setup_database`

```python
@pytest.fixture(scope="session")
async def setup_database(test_engine):
    async with test_engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)

    yield

    async with test_engine.begin() as conn:
        await conn.run_sync(Base.metadata.drop_all)

    await test_engine.dispose()
```

**`async def setup_database(test_engine)`** — эта фикстура **асинхронная**
(в отличие от предыдущей), потому что здесь уже происходит реальное
взаимодействие с базой данных (создание таблиц) — операция требующая `await`.

**`(test_engine)` в параметрах** — это **запрос другой фикстуры**. Pytest
видит что `setup_database` требует `test_engine`, находит фикстуру с этим
именем (ту что мы только что разобрали), выполняет её, и передаёт результат
сюда. Так строятся **цепочки зависимостей** между фикстурами — они могут
использовать друг друга, как и обычные функции с аргументами.

**`async with test_engine.begin() as conn:`** — открывает **транзакцию**
с базой данных. `test_engine.begin()` — асинхронный контекстный менеджер,
который автоматически:
- открывает соединение
- начинает транзакцию
- в конце блока (`async with`) — коммитит транзакцию если всё прошло без
  ошибок, либо откатывает если было исключение
- закрывает соединение

**`await conn.run_sync(Base.metadata.create_all)`** — вот здесь происходит
реальное создание таблиц. Разберём почему `run_sync`:

`Base.metadata.create_all` — это **синхронная** функция из "классического"
(не-async) SQLAlchemy API. В асинхронном коде нельзя просто взять и вызвать
синхронную функцию напрямую — она не поймёт что делать с асинхронным
соединением. `conn.run_sync(...)` — это специальный "мост": берёт синхронную
функцию, выполняет её в контексте текущего асинхронного соединения, и
оборачивает всё это в `await`-совместимую операцию.

**`yield`** — это ключевое слово превращает фикстуру в **генератор с паузой**.
Всё что было **до** `yield` — это код инициализации ("setup"), выполняется
один раз перед тем как тесты начнут работать. Всё что **после** `yield` —
код очистки ("teardown"), выполняется один раз **после того как ВСЕ тесты
использующие эту фикстуру завершились**.

Между `yield` и следующей строкой — pytest "замирает" здесь, передаёт
управление тестам, и возвращается сюда только когда вся тестовая сессия
подходит к концу.

**После `yield` — удаление таблиц:**
```python
async with test_engine.begin() as conn:
    await conn.run_sync(Base.metadata.drop_all)
```
Симметрично созданию — удаляет все таблицы, возвращая базу в пустое
состояние после того как тесты закончились.

**`await test_engine.dispose()`** — закрывает **сам движок** полностью,
освобождая все ресурсы (открытые соединения, если такие остались). Это
финальная уборка перед завершением тестовой сессии.

## Блок 5 — Фикстура `db_session`

```python
@pytest.fixture
async def db_session(test_engine, setup_database):
    session_factory = async_sessionmaker(test_engine, expire_on_commit=False)
    async with session_factory() as session:
        yield session
```

**`@pytest.fixture`** — без указания `scope`, значит по умолчанию
`scope="function"` — эта фикстура выполняется **заново для каждого отдельного
теста**. Это важно: каждый тест получает **свежую** сессию, изолированную
от других тестов.

**`(test_engine, setup_database)`** — запрашивает сразу **две** другие
фикстуры:
- `test_engine` — нужен движок чтобы создать фабрику сессий
- `setup_database` — здесь интересный момент: сама фикстура **не использует**
  результат `setup_database` напрямую (не сохраняет его в переменную), но
  указывает её как зависимость чтобы **гарантировать порядок выполнения**:
  таблицы должны быть уже созданы (через `setup_database`) прежде чем
  пытаться работать с сессией. Это способ явно сказать pytest "выполни
  сначала ту фикстуру, потом эту".

**`session_factory = async_sessionmaker(test_engine, expire_on_commit=False)`**:

`async_sessionmaker` — не сама сессия, а **фабрика**, которая умеет создавать
сессии по требованию — как класс `Session` который можно вызывать много раз
для создания разных экземпляров.

`expire_on_commit=False` — важный технический нюанс. По умолчанию SQLAlchemy
после каждого `commit()` помечает все объекты как "устаревшие" — при следующем
обращении к их атрибутам она заново пойдёт в базу за актуальными данными.
Это может привести к ошибкам в асинхронном коде (обращение к атрибуту после
commit может неожиданно попытаться сделать ленивый запрос к БД вне
асинхронного контекста — та самая ошибка `MissingGreenlet` которую ты уже
видел раньше). `expire_on_commit=False` отключает это поведение — объекты
остаются "живыми" со своими текущими значениями даже после коммита.

**`async with session_factory() as session:`** — создаёт реальный объект
сессии через фабрику и открывает его как асинхронный контекстный менеджер
(автоматически закроется в конце блока).

**`yield session`** — здесь снова пауза-генератор: отдаёт объект `session`
наружу (тесту или другой фикстуре, которая её запросит), и после того как
тест закончился — код продолжится после `yield` (в данном случае — просто
выйдет из `async with`, автоматически закрыв сессию).

## Блок 6 — Фикстура `client`

```python
@pytest.fixture
async def client(db_session: AsyncSession):
    async def override_get_db():
        yield db_session

    app.dependency_overrides[get_session] = override_get_db

    async with AsyncClient(
        transport=ASGITransport(app=app), base_url="http://test"
    ) as client:
        yield client

    app.dependency_overrides.clear()
```

Это самая важная фикстура — именно её запрашивает **каждый** твой тест,
потому что она даёт готовый HTTP-клиент для отправки запросов.

**`async def client(db_session: AsyncSession):`** — запрашивает `db_session`
(разобранную выше), и явно указывает тип через аннотацию `: AsyncSession` —
это чисто для читаемости кода и подсказок в IDE, не влияет на выполнение.

**`async def override_get_db(): yield db_session`** — создаёт **локальную
функцию** внутри фикстуры. Эта функция имитирует поведение оригинальной
`get_session` (тоже генератор с `yield`), но вместо создания **новой**
реальной сессии — просто отдаёт уже готовую тестовую `db_session`, которую
получили в параметре.

**`app.dependency_overrides[get_session] = override_get_db`** — это ключевая
строка всего механизма тестирования. `app.dependency_overrides` — специальный
словарь, встроенный в FastAPI именно для тестов. Он говорит:
"когда любой роутер внутри приложения попросит зависимость `get_session`
через `Depends(get_session)` — не вызывай настоящую `get_session` (которая
подключилась бы к реальной продакшн БД), а вызови вместо неё
`override_get_db`".

Это позволяет **не трогать сам код приложения** — роутеры продолжают писать
`Depends(get_session)` как обычно, они вообще не знают что их тестируют,
подмена происходит полностью снаружи.

**`async with AsyncClient(transport=ASGITransport(app=app), base_url="http://test") as client:`**:

`ASGITransport(app=app)` — это "транспорт" который говорит `AsyncClient`:
"не отправляй реальные пакеты по сети на какой-то внешний сервер — вызови
`app` (твоё FastAPI приложение) **напрямую в памяти**, как будто это и есть
сервер". ASGI (Asynchronous Server Gateway Interface) — это стандартный
протокол, по которому взаимодействуют веб-серверы (uvicorn) с приложениями
(FastAPI). `ASGITransport` эмулирует этот протокол без реального сетевого
стека — быстрее и не требует поднятого сервера на порту.

`base_url="http://test"` — фиктивный базовый адрес. Так как реального сервера
нет, этот адрес нужен просто чтобы `AsyncClient` мог сформировать полный URL
(например `http://test/api/products`), физически никуда он не стучится.

**`yield client`** — отдаёт готовый клиент тесту. Тест получает его как
параметр `client: AsyncClient` и использует `client.get(...)`, `client.post(...)`
и так далее.

**`app.dependency_overrides.clear()`** (после `yield`) — когда тест закончился,
убирает подмену зависимостей полностью, возвращая `get_session` к нормальному
поведению. Это важно для **изоляции тестов** — если бы подмена осталась,
следующий тест (или даже случайный запрос вне тестов) мог бы неожиданно
использовать тестовую сессию вместо настоящей.

## Блок 7 — Фикстура `clean_database`

```python
@pytest.fixture(autouse=True)
async def clean_database(db_session):
    from sqlalchemy import delete
    from app.models.categories import Category
    from app.models.products import Product
    from app.models.users import User

    yield

    await db_session.execute(delete(Product))
    await db_session.execute(delete(Category))
    await db_session.execute(delete(User))
    await db_session.commit()
```

**`@pytest.fixture(autouse=True)`** — новый параметр который мы ещё не
разбирали. `autouse=True` означает: эта фикстура выполняется **автоматически
для КАЖДОГО теста**, даже если тест **не запрашивает** её явно как параметр.
Обычные фикстуры активируются только когда тест указывает их имя в своих
параметрах — `autouse` фикстуры активируются всегда, без явного запроса.

**Локальные импорты внутри функции** (`from app.models.categories import
Category` и т.д., а не в начале файла) — это осознанный приём, часто
используемый чтобы **избежать циклических импортов** или просто чтобы не
загромождать верхнюю часть файла импортами, которые нужны только этой
конкретной фикстуре.

**`yield`** — здесь фикстура **сначала** отдаёт управление тесту (код до
`yield` пустой, только импорты), тест выполняется полностью, и только
**после** того как тест закончился — выполняется код очистки.

**Удаление данных после каждого теста:**
```python
await db_session.execute(delete(Product))
await db_session.execute(delete(Category))
await db_session.execute(delete(User))
await db_session.commit()
```

`delete(Product)` — SQLAlchemy Core конструкция, эквивалент SQL `DELETE FROM product`
(без `WHERE` — удаляет **все** строки таблицы). Три отдельных `delete()` вызова
для трёх таблиц — Product, Category, User.

**Важный момент — порядок удаления:**

Порядок `Product` → `Category` → `User` **не случаен**. `Product` имеет
foreign key на `Category` (`category_id`). Если бы попытались удалить сначала
`Category`, а `Product` всё ещё ссылался бы на неё — база данных выдала бы
ошибку нарушения внешнего ключа (`ForeignKeyViolation`). Поэтому сначала
удаляются "дочерние" записи (Product), потом "родительские" (Category).

**Зачем вообще нужна эта фикстура, если каждый тест и так использует новую
`db_session`:**

Хотя каждый тест получает **новую сессию** (через `db_session` с
`scope="function"`), сама **база данных (файл SQLite)** — общая на протяжении
всей тестовой сессии (`test_engine` с `scope="session"`). Если тест A создал
пользователя с email `test@test.com`, а тест B тоже попытается создать
пользователя с таким же email — возникнет конфликт "email уже занят", хотя
логически это два независимых теста. `clean_database` решает эту проблему,
очищая данные после каждого теста, чтобы следующий тест начинал с пустой
базы.

## Блок 8 — Фикстура `sample_product`

```python
@pytest.fixture(scope="function")
async def sample_product(db_session):
    from app.models.categories import Category
    from app.models.products import Product

    category = Category(name="Electronics", slug="electronics")
    db_session.add(category)
    await db_session.commit()
    await db_session.refresh(category)

    product = Product(
        name="Phone",
        price=999,
        category_id=category.id,
        description="Test phone description",
    )
    db_session.add(product)
    await db_session.commit()
    await db_session.refresh(product)

    return product
```

**`@pytest.fixture(scope="function")`** — здесь `scope="function"` указан
явно (хотя это и значение по умолчанию) — вероятно для ясности, чтобы явно
показать что для каждого теста создаётся **новый** товар, а не переиспользуется
старый.

**`(db_session)`** — запрашивает готовую сессию, чтобы напрямую работать
с базой данных, минуя HTTP-запросы (в отличие от того, как обычно тестируешь
через `client.post(...)`, здесь товар создаётся **напрямую через ORM**,
что быстрее и удобнее когда сам факт создания товара не является предметом
теста, а просто нужен как подготовительные данные).

**Создание категории:**
```python
category = Category(name="Electronics", slug="electronics")
db_session.add(category)
await db_session.commit()
await db_session.refresh(category)
```

- `Category(...)` — создаёт **объект в памяти Python**, ещё не в базе данных
- `db_session.add(category)` — помечает объект как "нужно сохранить" (добавляет
  в очередь на сохранение внутри сессии — это тоже пока не запрос к БД)
- `await db_session.commit()` — вот теперь реально отправляется `INSERT` запрос
  и фиксируется в базе
- `await db_session.refresh(category)` — обновляет объект `category` данными
  **из базы** — это важно, потому что после `commit()` в базе появляется
  автоматически сгенерированный `id` (через `SERIAL`/`AUTOINCREMENT`), но
  Python-объект в памяти о нём "не знает", пока явно не запросишь обновление
  через `refresh()`

**Аналогично создаётся товар**, но уже с `category_id=category.id` — обрати
внимание, к этому моменту `category.id` уже доступен именно благодаря
предыдущему `refresh()`.

**`return product`** — обычный `return`, не `yield`! Эта фикстура **не имеет
кода очистки** после теста — просто создаёт товар и отдаёт его. Очисткой
данных занимается отдельная фикстура `clean_database` (разобранная выше,
`autouse=True`), которая сработает после теста автоматически и удалит и
этот товар вместе со всеми остальными данными.

## Итоговая картина — как все фикстуры связаны между собой

```
test_engine (session scope)
    │
    ├──> setup_database (создаёт/удаляет таблицы, session scope)
    │        │
    │        └──> db_session (новая сессия для каждого теста)
    │                 │
    │                 ├──> client (HTTP-клиент с подменённой БД)
    │                 │
    │                 ├──> clean_database (autouse, чистит после каждого теста)
    │                 │
    │                 └──> sample_product (создаёт тестовый товар)
```

Когда тест пишет:
```python
async def test_get_all_products(client: AsyncClient, sample_product):
```

pytest видит два параметра, разворачивает всю цепочку зависимостей автоматически:
1. Создаёт `test_engine` (или берёт уже созданный, если это не первый тест
   в сессии)
2. Убеждается что `setup_database` выполнилась (таблицы созданы)
3. Создаёт свежую `db_session`
4. Через неё создаёт `client` (с подменённой зависимостью `get_session`)
5. Через неё же создаёт `sample_product` (реальный товар в базе)
6. Запускает тело теста с готовыми `client` и `sample_product`
7. После теста — `clean_database` очищает базу
8. `client` закрывает HTTP-соединение и снимает подмену зависимостей

Вся эта цепочка выполняется **автоматически**, тебе не нужно вручную вызывать
эти функции — достаточно указать нужные имена в параметрах теста.
